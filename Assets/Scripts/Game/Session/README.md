**Проект:** LunaticMagicV3

**Дата обновления:** 15 ноября 2026  

---

## 1. Фундаментальные Принципы и Разделение Ответственности

Игровая сессия (`GameSession`) представляет собой **изолированную песочницу конкретного игрового мира** (активный мир, время `LocalTime`, ввод `InputRouter`, звук `SessionSoundController`, сущности `EntitiesManager`).

Архитектура строго разграничивает три уровня:
1. **`Global` (`GlobalGame`, `BootstrapGlobalGame`, `UIGlobalState`)**:
   * Существует всегда (до, во время и после сессии).
   * Содержит системный оверлей (Консоль `~`, Дебаг-меню `F12`), физический ввод (`IInputController`) и настройки.
2. **`Session` (`GameSession`)**:
   * Управляет жизненным циклом сессии, вычисляет стейт (`SessionState`) и маршрутизирует ввод.
3. **`Entities` (`EntitiesManager`, `Entity`, `IFocusable`)**:
   * Объекты игрового мира, их компоненты и логика.

## 2. Переход от `IsPaused` к `IsGameplay`

Ранее в сессии использовался отрицательный флаг `IsPaused`, что приводило к постоянным двойным отрицаниям в коде (`if (!IsPaused)`).

**Принятое решение:**
* Основным низкоуровневым свойством сессии стал позитивный флаг `IsGameplay` (`ReactiveProperty<bool>`).
* Значение `true` однозначно сообщает всем подсистемам: *«Мир активен, симуляция тикает, управление передано в игровой процесс»*.
* `FixedUpdate`, `Update` и `LateUpdate` в `GameSession` используют `IsGameplay` для прозрачного разделения логики.

## 3. Вычисляемые Состояния Сессии (`SessionState` и `SessionPauseComputed`)

Стейт сессии не хранится в виде хаотично мутируемых переменных, а вычисляется функционально через `SessionPauseComputed.Computed(...)`.

Состояния представлены **полиморфными классами** (`SessionState`), каждый из которых задаёт своё поведение:

```
┌─────────────────────────┬──────────────┬─────────────┬────────────────────────────────────────┐
│ Состояние (SessionState)│  IsGameplay  │ Курсор      │ Аудио / Музыка                         │
├─────────────────────────┼──────────────┼─────────────┼────────────────────────────────────────┤
│ 1. InitialLoading       │    false     │ Locked      │ Слот 3 (LoadingTrack)                  │
│ 2. EntitiesSync         │    false     │ Locked      │ Слот 1 (GameplayTrack не прерывается)  │
│ 3. PauseScreen          │    false     │ Visible     │ Слот 2 (PauseTrack / тишина)           │
│ 4. Gameplay             │    true      │ По фокусу   │ Слот 1 (GameplayTrack)                 │
└─────────────────────────┴──────────────┴─────────────┴────────────────────────────────────────┘
```

### Логика вычисления приоритета:
```csharp
if (isSessionInitLoading)
    return SessionStates.InitialLoading; // 1. Стартовая загрузка сессии/сейва

if (isEntitiesSync)
    return SessionStates.EntitiesSync;   // 2. Стриминг чанков / блэкаут при телепорте

if (!isGameplay)
    return SessionStates.PauseScreen;    // 3. Меню паузы по Esc

return SessionStates.Gameplay;           // 4. Активный геймплей
```

## 4. Неочевидная Роль `UIGlobalState.IsAnyOpen`

Глобальный системный оверлей (Консоль `~`, Дебаг-меню `F12`) работает **намеренно в обход стейтов сессии**:

### Почему в сессии НЕТ стейта «Консоль»?
* Консоль и дебаг-меню живут на уровне `GlobalGame`. Они могут открываться в абсолютно любой момент: до создания сессии, во время начальной загрузки, в меню паузы или посреди боя.
* Если бы «Консоль» была стейтом сессии, это засорило бы сессионную логику и потребовало сложного стека возврата (куда вернуться после закрытия консоли: в паузу? в загрузку? в геймплей?).

### Как `IsAnyOpen` перехватывает управление снаружи:
`GlobalGame.UIGlobalState.IsAnyOpen` действует как **внешний приоритетный фильтр**:

1. **Курсор (`CursorState`)**:
   * `CursorState` напрямую подписан на `IsAnyOpen`.
   * При `IsAnyOpen == true` курсор **принудительно разблокируется и отображается** (`CursorLockMode.None`, `visible = true`).
   * При закрытии консоли (`IsAnyOpen == false`) курсор **автоматически возвращается** к тому режиму, который требует текущий стейт сессии или сущность в фокусе (например, обратно блокируется `Locked` для игрока).

2. **Маршрутизация ввода (`SessionInputRouter`)**:
   * Оба сессионных роутера (`InputRouterGameplay` и `InputRouterPause`) проверяют `!IsAnyOpen.Value`.
   * При открытии консоли **оба канала ввода сессии мгновенно затыкаются**: клавиши WASD, пробел и клики мыши перестают поступать в сессию, предотвращая случайные прыжки или перемещения персонажа во время набора текста в консоли.

3. **Заморозка симуляции**:
   * Консоль может иметь собственную локальную настройку (ставить `Time.timeScale = 0` или оставлять мир тикать в фоне для отладки в реальном времени), совершенно не затрагивая внутренние стейты сессии.

## 5. Два Канала Маршрутизации Ввода (`InputRouterGameplay` и `InputRouterPause`)

Сессия предоставляет два раздельных шлюза ввода:
1. **`InputRouterGameplay`**:
   * Активен только при `IsGameplay == true && !IsAnyOpen`.
   * Передаётся сущностям мира через `IFocusable.Focus(inputRouter)`.
   * При переходе в неактивное состояние **автоматически сбрасывает все оси и кнопки в дефолт** (`Vector2.zero`, `false`), генерируя события `OnUp` на зажатых клавишах. Это предотвращает залипание кнопок при открытии паузы или консоли.
2. **`InputRouterPause`**:
   * Активен только при `IsGameplay == false && !IsAnyOpen`.
   * Передаётся UI экрана паузы (слушает `Esc` для закрытия меню, стрелки навигации).

## 6. Аудиосистема Сессии (`Session/Pause/Sound`)

* Управляет 3 логическими слотами музыки: `GameplayTrack`, `PauseTrack`, `LoadingTrack`.
* Сериализует названия треков и актуальный таймкод `PlaybackTime` в файл сохранения `SessionSoundData`.
* **Характер переключения**: резкое прерывание при уходе на паузу/загрузку и резкое появление при возврате в геймплей с сохранённого таймкода (Cut).
* **Физический потребитель**: спавн и уничтожение дочернего `GameObject` с компонентом `AudioSource` внутри долгоживущего `BootstrapGlobalGame`.

## 7. Анализ Оставшихся Задач Системы

Для завершения полной рабочей цепочки сессии (за рамками системы сущностей и стриминга) необходимо реализовать:

1. **Создание Audio GameObject (Потребитель звука)**:
   * Реализация компонента/сервиса внутри `BootstrapGlobalGame`, который слушает активный трек сессии, спавнит дочерний `GameObject` с `AudioSource` и запускает воспроизведение.
2. **Жизненный цикл `IsSessionInitLoading` и `IsEntitiesSync`**:
   * `IsSessionInitLoading`: стартует со значением `true` при создании `GameSession`. Должен сбрасываться в `false` после завершения распаковки сейва и первой успешной инициализации сущностей мира.
   * `IsEntitiesSync`: должен взводиться в `true` при начале подгрузки чанков / телепорте сущности и сбрасываться в `false`, когда синхронизация завершена.
3. **Связка UI Toolkit со стейтами сессии**:
   * Подписка `SessionLayerComponent` на актуальный `SessionState` для автоматического открытия экрана паузы при `SessionStatePauseScreen` и экрана загрузки при `SessionStateInitialLoading`.




Мои пометки:

Два Канала Маршрутизации Ввода (`InputRouterGameplay` и `InputRouterPause`)
Ввод разделяется на 2 системы в зависимости от текущего GameSession.IsGameplay
Также перед вводом стоит `GlobalGame.UIGlobalState.IsAnyOpen` если он true то ввод вообще не идет в сессию.

Аудиосистема Сессии (`Session/Pause/Sound`)
Тут уже есть 3 трека с временем момента на котором должна восмпроизвестись мелодия. По сути прото выбирается какой трек щас продолжить (оставшиеся 2 остановить).
Сами треки поставляются отдельно, например сущностями (геймплейными триггерами)

Курсор
В курсоре принцип похож на Аудиосистему, но суть в том что когда `GlobalGame.UIGlobalState.IsAnyOpen` становится равен false то CursorState опрашивает текущий стейт сессии на то какой курсор щас поставить.
Также если щас игра (SessionStateGameplay) то поставщиком является сущность в фокусе, она меняет: 
только CursorStateMode в фокусе, а SessionStateGameplay просто берет курсор у фокуса
