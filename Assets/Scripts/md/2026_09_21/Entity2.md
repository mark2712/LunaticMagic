# Архитектура Стриминга и Уровней Сущностей (Entity 2)

**Проект:** LunaticMagicV3  
**Назначение:** Практическая реализация стриминга сущностей (CullingGroup vs Префиксные структуры) и синхронизация уровней загрузки (L1–L4).

---

## 1. Основное Решение: Unity `CullingGroup` API

Встроенный в Unity C++ механизм для кастомных LOD-ов, стриминга и толпы NPC.

### 1.1. Почему идеально подходит для Уровня 1 (L1)
* **GameObject НЕ ТРЕБУЕТСЯ:** `CullingGroup` оперирует обычным плоским массивом легковесных C# структур `BoundingSphere[]` (Vector3 позиция + float радиус).
* **Сущности на L1 остаются чистыми C# классами в памяти:** Нет компонентов `Transform`, нет физики, нет `MonoBehaviour`.

### 1.2. Прямой маппинг на полосы дистанций (Distance Bands)
```csharp
cullingGroup.SetBoundingDistances(new float[] { 30f, 50f, 100f });
cullingGroup.SetDistanceReferencePoint(focusTargetTransform);
```
* **Band 0 (0..30м) $\rightarrow$ Целевой L4:** Полный визуал, подгрузка VRM 1.0 модели, аниматор.
* **Band 1 (30..50м) $\rightarrow$ Целевой L3:** Активная локомоция, разморозка физики (`isKinematic = false`), NavMesh.
* **Band 2 (50..100м) $\rightarrow$ Целевой L2:** Замороженный коллайдер (`isKinematic = true`), физическое присутствие.
* **Band 3 (>100м) $\rightarrow$ Целевой L1:** Виртуальные данные в памяти. Физический GameObject уничтожен/возвращен в пул.

### 1.3. Событийная модель и Frustum Culling
* Переходы между уровнями происходят по событиям: `cullingGroup.onStateChanged += OnStateChanged`. Никаких ручных циклов перебора в `Update()`.
* **Frustum culling из коробки:** Параметр `evt.isVisible` сообщает, видна ли сущность в кадре камеры прямо сейчас (можно экономить на анимациях за спиной игрока даже на L4).

## 2. Альтернативное Алгоритмическое Решение: Префиксное Пространственное Дерево (Spatial Trie / Radix)

Решение, основанное на поразрядном делении координат и префиксном поиске за $O(1)$.

### 2.1. Концепция в 1D (Разряды как масштаб)
Если представить координату по разрядам: `0000003571`:
* Разряд тысяч ($10^3$) = `3`
* Разряд сотен ($10^2$) = `5`
* Поиск диапазона $1000$ м (от 3571 до 4571) не спускается к единицам, а за 2 обращения берет бакеты разряда тысяч: `[...][3]` и `[...][4]`.

### 2.2. Как математика и CS переносят это в 2D (Плоскость XZ)

#### Теория: Space-Filling Curves и Z-Order (Morton Code / Quadtree)
Чтобы перенести 1D-префиксное дерево в 2D, информатика использует **интерливинг (переплетение) разрядов**:
* Каждому уровню масштаба соответствует пара координат $(X, Z)$:
  - **Разряд тысяч:** Квадрат сектора $1000 \times 1000$ метров: $(X_{\text{тыс}}, Z_{\text{тыс}})$
  - **Разряд сотен:** Квадрат ячейки $100 \times 100$ метров внутри сектора: $(X_{\text{сот}}, Z_{\text{сот}})$

#### Практическая 2D структура данных (Иерархические Чанки):
Чтобы избежать сотен микро-словарей на каждый разряд, структура упаковывается в 2 уровня:
```csharp
// [Локация][Сектор 1000м (Vector2Int)][Ячейка 100м (Vector2Int)] -> HashSet<EntityRuntime>
Dictionary<string, Dictionary<Vector2Int, Dictionary<Vector2Int, HashSet<EntityRuntime>>>> _spatialTrie;
```
1. **Поиск окрестности 1000м:** За $O(1)$ опрашивается сектор игрока и 1–3 смежных сектора.
2. **Поиск окрестности 100м (зона L4/L3):** Опрашиваются только ячейки сотен внутри текущего сектора.

### 2.3. Сравнение подходов
* **`CullingGroup` (Рекомендуется для Unity-клиента):** Нативный C++, считает сферы и видимость камеры автоматически, нулевой оверхед на C#.
* **`Spatial Trie` (Рекомендуется для Сервера / Headless симуляции):** Полностью data-driven C#, не зависит от движка Unity, идеален для серверного A-Life и фоновой симуляции мира.

## 3. Синхронизация и Асинхронная Загрузка Сейвов

### 3.1. Проблема
Асинхронная инициализация может привести к провалам сущностей сквозь пол или обращению к еще не созданным коллайдерам.

### 3.2. Трехфазная Загрузка с Барьером Синхронизации
```
                  [ СЕЙВ НА ДИСКЕ ]
                          │
                          ▼
┌──────────────────────────────────────────────────────────────┐
│ ФАЗА 1: Мгновенное C# восстановление Данных (L1)             │
│   • Создаются все EntityRuntime в памяти за 1 кадр           │
│   • Восстанавливаются ID, ХП, квесты, инвентарь, связи       │
│   • Физика Unity выключена, GameObject'ов на сцене нет       │
└──────────────────────────────┬───────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ ФАЗА 2: Расчет целевых уровней (Target Tiers)                │
│   • Находим позицию фокусной сущности (игрока)               │
│   • Через CullingGroup / Spatial Trie определяем TargetTier: │
│     - Фокусная сущность: Target L4                           │
│     - 0..30м: Target L4 | 30..50м: Target L3                 │

└──────────────────────────────┬───────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ ФАЗА 3: Барьер Синхронизации (Под Loading Screen)            │
│   1. Загрузка террейна и статических коллайдеров сцены       │
│   2. Спавн GameObject для целевых L2/L3 (isKinematic = true) │
│   3. Асинхронная подгрузка 3D-моделей (VRM) для целевых L4   │
│   4. Ожидание готовности всех задач зоны видимости           │
│   5. БАРЬЕР ПРОЙДЕН: Включение физики (isKinematic = false)  │

```

## 4. Переход уровней во время геймплея (Runtime Tier Pipeline)

В процессе игры сущность не прыгает через уровни хаотично, а идет по строгой лесенке:
$$L1 \rightleftarrows L2 \rightleftarrows L3 \rightleftarrows L4$$

* **L1 $\rightarrow$ L2:** Выделение легковесного `GameObject` с коллайдером. `Rigidbody.isKinematic = true`.
* **L2 $\rightarrow$ L3:** Активация локомоции, `isKinematic = false`, включение NavMesh / гравитации.
* **L3 $\rightarrow$ L4:** Прикрепление визуала (VRM-модели из пула), включение аниматора.
* **L4 $\rightarrow$ L3:** Возврат модели в пул, отключение аниматора (физика еще жива).
* **L3 $\rightarrow$ L2:** Заморозка физики (`isKinematic = true`).
* **L2 $\rightarrow$ L1:** Уничтожение/возврат в пул физического `GameObject`. Сущность остается чистой записью `EntityRuntime` в памяти.
